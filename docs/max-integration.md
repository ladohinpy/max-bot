# Интеграция с MAX

Документация MAX проверена **1 ноября 2026 года**. Этот документ описывает путь от локальной симуляции MyBoxFoxel к работающему мини-приложению. Проект по умолчанию использует вымышленные данные и не связан с аккаунтами MAX или Фоксфорда.

## Как приложение попадает в MAX

Мини-приложение MAX — веб-приложение на HTML, JavaScript и CSS, размещённое на внешнем HTTPS-хостинге. По текущей документации оно обязательно привязывается к чат-боту. React и библиотека MAX UI доступны, но не обязательны: выбранный в MyBoxFoxel vanilla JavaScript совместим с этой моделью.

```text
Публикация в канале Фоксфорда
  → ссылка https://max.ru/<botName>?startapp=<payload>
  → привязанное к боту мини-приложение
  → HTTPS-сервер MyBoxFoxel
  → авторизация MAX
  → отдельная привязка профиля Фоксфорда
  → данные, доступные этому профилю
```

Канал служит точкой входа. Приложение технически подключается к боту, а не непосредственно к каналу. Сам переход по `startapp` может открыть приложение без запуска диалога с ботом.

Для подключения требуются верифицированный профиль на платформе MAX для партнёров, бот, его модерация и HTTPS-адрес приложения. По документации платформа доступна юридическим лицам, ИП и самозанятым — резидентам РФ. Возможность создать профиль и права на канал/бота нужно проверить в аккаунте организации перед реальным запуском.

Источники: [Подключение мини-приложения](https://dev.max.ru/docs/webapps/introduction/), [Подключение к платформе](https://dev.max.ru/docs/maxbusiness/connection/), [Создание и модерация бота](https://dev.max.ru/docs/chatbots/bots-create/create/).

## Данные запуска и авторизация MAX

Официальный Bridge подключается по адресу `https://st.max.ru/js/max-web-app.js` и предоставляет `window.WebApp`.

| Данные | Назначение | Что они не подтверждают |
| --- | --- | --- |
| `WebApp.initData` | Исходная подписанная строка для серверной проверки | Права на профиль Фоксфорда |
| `WebApp.initDataUnsafe` | Разобранные данные для интерфейса: пользователь, чат, параметры запуска | Подлинность пользователя без серверной проверки |
| `user.id` после проверки подписи | Идентификатор пользователя MAX | Значение `FoxfordID`, родство или право видеть ребёнка |
| `start_param` | Источник перехода или запрошенный экран | Право доступа к объекту, указанному в параметре |
| `auth_date` | Время выдачи стартовых данных в Unix-секундах | Бессрочную действительность данных |

Доверять `initDataUnsafe.user.id` или `userId`, который прислал браузер, нельзя. Сервер должен получить исходную строку `initData`, проверить её подпись и свежесть, а затем извлечь `user.id` из проверенных параметров.

MyBoxFoxel предусматривает `POST /api/max/session` с JSON-телом `{ "initData": "..." }`. Проверка доступна только при заданном на сервере `MAX_BOT_TOKEN`. Даже успешная проверка MAX не создаёт связь с Фоксфордом и не превращает демонстрационные данные в реальные.

После проверки сервер выдаёт собственную случайную cookie с `HttpOnly`, `SameSite=Lax` и сроком не более часа. Сессии хранятся в памяти до перезапуска. При HTTPS-размещении следует включить `COOKIE_SECURE=true`. Исходная строка запуска не сохраняется и не логируется. Полный контракт endpoint описан в [архитектуре](architecture.md).

### Проверка подписи

Основа алгоритма взята из официальной документации. Отклонение повторяющихся ключей и сравнение без утечки времени — дополнительные проверки нашей реализации:

1. Разобрать строку `initData` на параметры, отклонить повторяющиеся ключи и убедиться, что `hash` присутствует один раз.
2. Сохранить `hash`, исключить его из данных для подписи.
3. URL-декодировать значения ровно в соответствии с форматом исходной строки; не декодировать повторно уже разобранные значения.
4. Отсортировать параметры по именам и объединить пары `key=value` символом перевода строки `\n`.
5. Вычислить `secret_key = HMAC_SHA256(key="WebAppData", data=MAX_BOT_TOKEN)`.
6. Вычислить `expected_hash = HEX(HMAC_SHA256(key=secret_key, data=prepared_params))`.
7. Сравнить подписи без утечки времени сравнения и проверить допустимый возраст `auth_date`. Документация рекомендует интервал один час.

Токен бота хранится только на сервере. Его нельзя включать в `dist`, передавать браузеру или коммитить в Git. Нужна также защита собственного механизма сессий: проверка подписи на входе сама по себе не реализует управление сессиями, отзыв доступа и контроль прав.

Источники: [MAX Bridge](https://dev.max.ru/docs/webapps/bridge/), [Валидация данных](https://dev.max.ru/docs/webapps/validation/).

## Привязка к профилю Фоксфорда

Это проектируемая интеграция; в локальной версии она **не реализована**. Конкретный механизм зависит от внутренней системы авторизации и доступных API Фоксфорда. Открытые контракты этих систем в рамках проекта не подтверждены.

Предпочтительный сценарий:

1. Пользователь открывает мини-приложение; сервер проверяет подпись MAX и создаёт короткоживущий запрос на привязку.
2. Пользователь явно выбирает «Привязать профиль» и переходит в доверенный контур авторизации Фоксфорда.
3. После успешной авторизации сервер Фоксфорда подтверждает профиль и его права; пользователь подтверждает связь с MAX.
4. Сервер выдаёт одноразовый непрозрачный код, связанный с запросом, профилем и сроком действия. Код передаётся в доверенный обратный переход и погашается сервером один раз.
5. MyBoxFoxel сохраняет проверенную связь `max_user_id ↔ foxford_user_id`. Запросы к данным выполняются с повторной проверкой принадлежности профиля и прав на ребёнка.

Код привязки должен быть короткоживущим, непредсказуемым, одноразовым и связанным с инициатором. Для реального контура нужны защита от подмены запроса (`state`), повторного использования кода, привязки к другому пользователю и незаметного перепривязывания. Отдельно предусматриваются отзыв связи и повторная авторизация. Нельзя отдавать данные ребёнка по одному идентификатору в URL.

Альтернативная точка входа — кнопка в уже авторизованном кабинете Фоксфорда, которая создаёт такой одноразовый код и открывает MAX по диплинку. Код не должен содержать персональные данные, и сам факт наличия кода в URL не отменяет серверную проверку.

## Телефон и диплинки

Телефон не входит автоматически в обычные данные пользователя MAX. Метод `WebApp.requestContact()` показывает нативный запрос с согласием и возвращает `phone`, `authDate`, `hash`. Для этих данных документация описывает отдельную проверку подписи. Подтверждённый телефон MAX ещё не доказывает право доступа к конкретному ребёнку в Фоксфорде.

`startapp` принимает до 512 символов: латинские буквы, цифры, `_` и `-`. Для источника перехода можно использовать условное значение `channel_profile`. Для конфиденциального контекста документация рекомендует одноразовые токены. Не следует передавать в payload открытые персональные данные или долговечные секреты.

`WebApp.openLink()` открывает внешний браузер и требует пользовательского клика. `WebApp.openMaxLink()` открывает ссылки MAX внутри мессенджера. Эти переходы нужно проверить на целевых клиентах MAX; локальная браузерная симуляция не доказывает их работу внутри мессенджера.

Источник: [MAX Bridge](https://dev.max.ru/docs/webapps/bridge/), [Диплинки и подключение приложения](https://dev.max.ru/docs/webapps/introduction/).

## Путь к реальному запуску

1. Согласовать набор экранов и проверить сценарии на демонстрационных данных: непривязанный профиль, родитель, выбор ребёнка, достижения, пустые данные и ошибки.
2. Зафиксировать реальные контракты Фоксфорда: авторизация, права родителя/ученика, дети, занятия, прогресс и достижения. Реализовать серверный адаптер вместо демонстрационного хранилища.
3. Реализовать привязку, собственные сессии, отзыв доступа и серверную авторизацию всех запросов. Отдельно проверить, что пользователь не может получить данные чужого ребёнка.
4. Подготовить HTTPS-размещение, верифицированный профиль MAX и прошедшего модерацию бота. Подключить URL приложения в настройках бота.
5. Проверить приложение в MAX на Android, iOS, desktop и web, включая отказ от разрешений, просроченный запуск и возврат из авторизации Фоксфорда.
6. Разместить ссылку на приложение в своём канале после проверки реального контура и настройки поддержки.

Автоматические CRM-уведомления не входят в локальный прототип. По п. 1.5 текущих требований MAX авторизационные, транзакционные, сервисные и массовые маркетинговые сообщения через интеграцию допускаются только в случаях, предусмотренных договором с MAX. Наличие технического API не означает согласованный канал рассылки. Источник: [Требования к приложениям](https://dev.max.ru/docs/legal/requirements/).
