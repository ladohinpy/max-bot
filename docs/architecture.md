# Архитектура MyBoxFoxel

MyBoxFoxel — локальная симуляция кабинета внутри мини-приложения MAX и небольшая основа для проверки данных запуска MAX. Сведения о профилях, детях и обучении вымышлены. Реальная интеграция с Фоксфордом отсутствует.

## Компоненты

```text
Браузер или webview MAX
  │
  ├─ dist/: интерфейс и локальные демонстрационные данные
  │
  └─ тот же origin: /api/*
        │
        ├─ server.mjs: HTTP, статические файлы, сессии
        └─ src/max-auth.mjs: подпись MAX и auth_date

Будущий контур, сейчас отсутствует:
        сервер авторизации/привязки → API Фоксфорда → реальные данные
```

Стек: Node.js 22+, стандартные серверные модули Node.js, браузерные ES modules, HTML и CSS. Установка зависимостей и сборка не требуются; `dist` содержит готовые статические исходники. Запуск — `npm start`, локальный адрес — `http://localhost:4173`.

Официальный MAX Bridge загружается динамически при наличии признака запуска `WebAppData`. В обычном локальном браузере интерфейс работает на демонстрационных данных. SDK служит мостом с клиентом MAX; он не предоставляет учебные данные Фоксфорда.

## Интерфейс и демонстрационные данные

`dist/index.html` загружает `app.js`, `demo-data.js`, `max-bridge.js` и `styles.css`. В интерфейсе предусмотрены разделы главной страницы, детей, статистики, заданий, достижений и профиля. Состояния включают выбор ребёнка, базовый/расширенный демонстрационный сценарий, выбор одной из трёх учебных недель, поиск и фильтры заданий, категории достижений и модальные окна.

`dist/demo-data.js` экспортирует `DEMO_PARENT`, `CHILDREN`, `WEEKS`, `COURSES`. Демонстрационные дети содержат предметы (`subjects`), недельную статистику (`weeks`), задания (`tasks`) и достижения (`achievements`). Это локальный формат макета; он не заявлен как контракт настоящего API Фоксфорда.

В `localStorage` допускается только демонстрационный прогресс выполнения заданий (`foxel-demo-progress-v1`). Токены и данные запуска MAX туда не записываются. Сброс демонстрации не меняет реальные аккаунты.

## Три разных состояния доверия

1. **Демонстрация.** Пользователь выбирает вымышленные профили и сценарии. Это состояние не подтверждает ничью личность.
2. **Подтверждён MAX.** Сервер проверил подписанную строку и создал свою сессию. Известна личность пользователя MAX, но профиль Фоксфорда не привязан.
3. **Привязан Фоксфорд.** Проектируемое состояние после отдельного подтверждения профиля и прав. В текущей версии отсутствует; API всегда возвращает `foxfordLinked: false`.

Нельзя использовать переключение демонстрационного профиля как серверную авторизацию. Наличие MAX-сессии не даёт права показывать реальные данные ребёнка.

## Текущее серверное API

Все обращения выполняются к тому же origin, что и интерфейс. Значения из MAX не смешиваются с демонстрационными учебными данными.

### `GET /api/health`

```json
{
  "ok": true,
  "mode": "demo",
  "maxConfigured": false,
  "foxfordConnected": false
}
```

`maxConfigured` показывает только наличие серверной конфигурации токена. Даже при `true` поле `mode` остаётся `demo`, а `foxfordConnected` — `false`.

### `GET /api/max/session`

Без действующей cookie:

```json
{
  "authenticated": false,
  "identityVerified": false,
  "identity": null,
  "foxfordLinked": false
}
```

После успешной проверки MAX `authenticated` и `identityVerified` равны `true`, а `identity` содержит `{ "maxUserId": "…", "firstName": "…" }`. `maxUserId` передаётся строкой. Это отдельное пространство идентификаторов, не `FoxfordID`.

### `POST /api/max/session`

Тело запроса:

```json
{
  "initData": "<исходная подписанная строка MAX>"
}
```

| Результат | HTTP | Ответ |
| --- | --- | --- |
| `MAX_BOT_TOKEN` не задан | `503` | `{ "error": "max_not_configured" }` |
| Данные запуска не прошли проверку | `401` | `{ "error": "invalid_init_data" }` |
| Проверка успешна | `200` | Подтверждённая MAX-сессия и cookie |

Дополнительные ответы сервера: `400 invalid_json` при невалидном JSON, `403 origin_not_allowed` при постороннем browser origin, `413 body_too_large` при теле свыше 64 КиБ, `415 json_required` при другом `Content-Type`, `503 session_capacity` при заполнении лимита сессий. Для неподдерживаемого метода возвращается `405 method_not_allowed`. Запрос нужно отправлять с `Content-Type: application/json`.

Успешный ответ:

```json
{
  "authenticated": true,
  "identityVerified": true,
  "identity": {
    "maxUserId": "<подтверждённый ID MAX>",
    "firstName": "<имя из подписанных данных>"
  },
  "foxfordLinked": false
}
```

Сервер проверяет HMAC, уникальность ключей, наличие подписанных параметров и свежесть `auth_date`. Собственная сессия использует случайную cookie `HttpOnly`, `SameSite=Lax` и срок не более часа. Сервер хранит сессии в памяти; перезапуск их сбрасывает. Для HTTPS-размещения требуется `COOKIE_SECURE=true`. Это основа прототипа, без распределённого хранилища сессий и полноценного управления доступом Фоксфорда.

Исходная строка `initData` не хранится, не логируется и не помещается в `localStorage`. Токен бота не передаётся клиенту.

### `DELETE /api/max/session`

Удаляет собственную MAX-сессию и очищает cookie. Возвращает объект с `authenticated: false`, `identityVerified: false`, `identity: null`, `foxfordLinked: false`. Выход из этой сессии не завершает вход пользователя в приложение MAX.

Endpoint для реальной привязки Фоксфорда в текущей версии отсутствует.

## Контракты будущей интеграции с Фоксфордом

Ниже — предлагаемая модель, а не обнаруженные API Фоксфорда. До реализации нужно согласовать реальные названия, типы, права доступа и источники каждого поля.

| Объект | Минимальные данные | Что нужно определить |
| --- | --- | --- |
| Связь аккаунтов | `maxUserId`, `foxfordUserId`, время подтверждения, статус связи | Кто подтверждает связь, как отозвать и перепривязать |
| Профиль | Идентификатор, отображаемое имя, роль родителя/ученика | Авторитетный источник роли и срок действия доступа |
| Ребёнок | Идентификатор, имя, класс/уровень при наличии | Проверка связи с текущим родителем на сервере |
| Занятие | Идентификатор, название, начало, часовой пояс, статус, разрешённая ссылка | Какие продукты поддерживаются и откуда приходят изменения |
| Прогресс | Период, число выполненных заданий, метрики с единицами | Формулы, границы периода, знаменатель процентов, свежесть |
| Достижение | Идентификатор, название, дата, описание, ссылка на документ при наличии | Правила выдачи, доступность диплома, право скачивания |
| Доступ к продукту | Продукт, статус, период действия | Что именно означает полный/ограниченный доступ |

Для каждого ответа нужны понятные состояния `нет данных`, `данные загружаются`, `доступ запрещён`, `ошибка источника`, а также время обновления. Пустая статистика не должна автоматически отображаться как нулевой результат или низкая успеваемость. Числа и подписи демонстрации не задают формулы реальных метрик.

Серверный адаптер должен выдавать только разрешённые поля. Идентификатор ребёнка из URL или тела запроса следует проверять относительно подтверждённого профиля. Разные роли и несколько детей проверяются отдельно. Ссылки на уроки и дипломы должны приходить из доверенного источника; не нужно вычислять их по шаблону.

## Развитие

Локальная версия позволяет согласовать интерфейс и проверить часть механизма входа MAX. Для реального кабинета остаются авторизация и API Фоксфорда, одноразовая привязка, проверка прав на каждый объект, постоянное хранилище, HTTPS-размещение и проверка в клиентах MAX. Модель безопасной привязки и официальные источники описаны в [интеграции MAX](max-integration.md).

GitHub хранит исходный код проекта. Публикация репозитория не подключает бота, не проходит модерацию MAX и не публикует работающий сервер.
